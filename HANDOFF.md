## 1. What this project is

DSA replaces a Power BI dashboard (`TBL.pbix`, in the parent `OOTP-Analysis` folder, kept for reference) that visualized player ratings, prospect rankings, team rankings, and draft boards for an OOTP Baseball online league ("TheBigLeague"). Instead of Power BI reading manually-exported CSVs, this project pulls live from **StatsPlus** (a third-party web platform the league already uses) into a **Supabase Postgres database**, computes the same proprietary rating system Power BI used (now via TypeScript instead of DAX), and will serve it through a **Next.js** front end on **Vercel**.

Reference docs, in the order you'd actually want to read them if you need the "why":
- [`power-bi-rating-system-analysis.md`](../power-bi-rating-system-analysis.md) (parent dir) — the original Power BI rating engine, reverse-engineered formula by formula, plus the 4 harmonization decisions applied when porting it here.

- [`lib/database.types.ts`](lib/database.types.ts) — **the actual current schema**, auto-generated from the live database. Regenerate anytime with the Supabase MCP `generate_typescript_types` tool, or ask whoever's running the backend session to.

**✅ RLS is now ON, default-deny, as of 2026-08-19.** Every table has Row Level Security enabled with **zero policies** — meaning only the `service_role` key can read or write anything; the anon/public key gets nothing. This is intentional and expected to stay this way, not a temporary state to "finish" with policies later:

- All existing code (ingestion scripts, front-end server components) uses `service_role` server-side only and is completely unaffected — verified working after enabling.
- **RLS is NOT automatic on a new table.** Caught 2026-08-19: `prospect_bios` (created same day) shipped with RLS *disabled* — a real gap, exposed to the anon key — until the Supabase advisor caught it on an unrelated query days later. Any new `create table` needs its own explicit `alter table ... enable row level security;`, same migration or a follow-up — it does not inherit the project-wide default-deny posture automatically.
- **Why default-deny is the permanent design, not just the current one:** Overall/Potential rounding (hiding exact scout ratings from other GMs) happens in the React display layer, not the database. If anon ever got read access to the raw tables, someone could skip the UI and query Supabase's REST API directly for full-precision values. Routing every read through the Next.js server keeps that rounding meaningful.
- **Practical implication for you:** if you ever add client-side (browser) Supabase calls, they will get zero rows back — not an error, just empty results — until/unless a real anon policy is deliberately added for that specific case. If you hit unexplained empty data and you're using the anon key from the browser, this is almost certainly why. Default to querying through Next.js Server Components (the existing pattern) instead.

## 4. Data model — what actually exists

Three layers, all in `lib/database.types.ts`:

### Raw reference data (current-state, upserted each refresh)
`teams`, `players`, `contracts`, `contract_extensions`, `draft_picks`. Field names match StatsPlus's own naming, not relabeled. `players.pos`/`.bats`/`.throws` are StatsPlus's own numeric codes (not letter codes) — decode via `player_ratings_snapshots.pos` instead if you need a letter code like "SP"/"CF". `players.league_id` carries a non-obvious sign convention for level-1 rows — see gotcha 11.

### Raw time-series snapshots (every refresh adds new rows, tagged by `refresh_run_id`)
`player_batting_stats_snapshots`, `player_pitching_stats_snapshots`, `player_fielding_stats_snapshots`, `team_batting_stats_snapshots`, `team_pitching_stats_snapshots`, `player_ratings_snapshots`, `game_results`. **Important:** a player can have multiple stat rows for the same year — one per level they played at (promotions/demotions mid-season). Always filter/group by `level_id` when showing season stats, not just `year`. See §6 for the level-code decode table.

### Computed (rating engine output — never recompute in the front end, just read)
`player_computed`, `team_computed`. Holds `overall`, `potential`, `prospect_potential`, `role`, `sp_rp`, `tbl_pos`, `platoon`, `eta`, and every rank (`rank`, `org_rank`, `prospect_rank`, `prospect_org_rank`, etc.), all tied to a `refresh_run_id` and a `weights_id` (which `rating_weights` row produced them — weights are database rows, not hardcoded, specifically so methodology can be tuned/tested later). **`rating_weights` gained 9 new columns 2026-08-27** (the Contact/Control floor gates + age-developed threshold) — see gotcha 30. **New sibling table `player_projected_splits`, 2026-08-28** — an extrapolated Potential L/R split profile per player per refresh (10 tool grades × L/R), same no-FK/join-by-key pattern as this table — see gotcha 32. **`eta`'s formula changed 2026-08-31**: rounds the years-to-climb distance UP now (was nearest), and floors at `currentYear + 1` for everyone once the league's in its playoffs (`refresh_runs.game_date`'s month ≥ 10) — a same-year ETA stopped making sense once that year's season had already finished. **New columns `comp_player_id`/`comp_similarity`, also 2026-08-31** — the nearest established-MLB-player comp for a prospect (potential grades vs. an established player's current grades, same role bucket, weighted by `rating_weights`). Full methodology: `prospect-comp-methodology.md`. **`scripts/compute-team-ratings.ts`'s farm-system scoring was rewritten the same day** (Rees's spec): `minors_rank`/`batting_prospect_rank`/`pitching_prospect_rank`/`tbl_readiness_rank` are still the same column names, but now driven by a "Blue-Chip + Depth" formula (top 3 prospects per H/P split count in full, everyone lower decays by rank) combined with an explicit balance penalty so a lopsided batting-only or pitching-only system can't out-rank a well-rounded one — replaces the old flat top-20-average port of the Power BI "RLB" system. New `system_rank_weights` table (mirrors `rating_weights`' pattern) holds the tunable coefficients; new `team_computed.balance_index` column is a display-only 0-1 "how lopsided" stat. Full methodology: `system-rank-methodology.md`. See gotcha 34 for a real bug this same-day migration introduced elsewhere and how it was fixed. **New columns `blue_chip_score`/`depth_score`, also 2026-08-31** — the combined batting+pitching Blue-Chip and Depth components broken out separately (they already summed into `minor_league_batting_rating`/`minor_league_pitching_rating`; these are purely a display decomposition for the rebuilt System Rankings cards' 3-way grade breakdown, not a new number). **New table `org_system_bios`** — hand/AI-written system-analysis paragraph per org, same infrastructure pattern as `prospect_bios` (ships empty; the writing pass is a separate follow-up step). **`overall`/`potential`/`prospect_potential` are CALIBRATED values as of 2026-09-03, not raw formula output** — see "Hitter/pitcher rescale" below for the full mechanism (per-type z-score above the real MLB mean, a level-anchored piecewise-linear ladder below it, recomputed fresh every refresh). New sibling columns `overall_raw`/`potential_raw`/`prospect_potential_raw` hold the formula's untransformed output for the few consumers that need it. New `rating_weights.relief_value_multiplier` (2026-09-03) and the Contact/Control gate rework (2026-09-04, age-based → per-tool "fully developed") are covered in the same section, along with the corrected 8-tier level scale (`effectiveLevel()` in `lib/display-helpers.ts`) and new table `calibration_level_anchors`.

**System Rankings page rebuilt into cards, 2026-08-31** (`/TBL/prospects/farms`, Rees's spec) — same card language as Top Prospects (`.prospect-card--clickable`/`.prospect-bio-expanded` reused verbatim for the org-analysis toggle), but allowed to run taller: team header with all 4 ranks color-coded via the same `percentileStyle()` gradient used on `/players`/`/draft`/`/org-minors`, a two-column top-5-hitters/top-5-pitchers breakdown, and a Blue-Chip/Depth/Balance grade-word breakdown (NOT the underlying numbers, per Rees's spec). New query module `lib/system-rankings-query.ts` (`getSystemRankingsDetailed()`) and component `app/_components/SystemRankingsCards.tsx` power this specifically — the OLD `getTeamRankings()`/`TeamRankingsTable.tsx` are UNCHANGED and still power `/prospects`' compact side-by-side rankings column, which doesn't have room for these taller cards. **Balance Index grading, settled after a same-day back-and-forth**: briefly switched to fixed ABSOLUTE thresholds (0.90/0.75/0.55/0.35) after noticing the whole league clusters tightly at 0.85-0.98 balance, which made percentile grading put an objectively fine 0.91 at "Below Average" just because a few orgs sat higher. That in turn caused the opposite real problem Rees caught immediately: Steam graded "Plus" balance (0.85 clears the absolute bar) despite a #3 batting rank next to a #27 pitching rank -- a genuinely lopsided system competitively. **Reverted to percentile-among-orgs**, same as Blue-Chip/Depth, on Rees's explicit call: balance should reflect standing relative to the rest of the league, not an absolute ratio read in isolation. Full back-and-forth: system-rank-methodology.md §5a.

**`role` for position players was redesigned 2026-08-20** (pitchers unchanged — still `sp_rp`-based). Old formula used only composite *current*-ability ratings (`cRating`/`infRating`/`ofRating`) with a coarse INF/UTIL/C/OF bucket set. New formula, Rees's spec, in `lib/rating-engine.ts`'s `ROLE_BUCKET_THRESHOLDS`: seven buckets — **C → SS → CF → INF → COF → 1B → DH** — evaluated in that priority order, first match wins, mixing *potential* position-fit grades (`pot_c`/`pot_ss`/`pot_cf`/`pot_lf`/`pot_rf`/`pot_1b`) with *current* range grades (`ifr`/`ofr` — no potential-range field exists in this data). Exact cutoffs: C `pot_c≥50`; SS `pot_ss≥55` + `ifr≥65`; CF `pot_cf≥55` + `ofr≥65`; INF (2B/3B) `ifr≥50` alone, no position-potential gate; COF `max(pot_lf,pot_rf)≥50` + `ofr≥50`; 1B `pot_1b≥55`; DH is the pure fallback (didn't clear any bar). Verified against 8 known players spanning every non-DH bucket, including two priority-order edge cases (a player with qualifying `pot_1b` correctly landing INF instead, since INF is checked first). Distinct from `tbl_pos` (still unchanged — lists *every* position a player's potential clears a bar for, not a single bucket).

### Draft class tracking
`draft_class_imports` / `draft_class_pool_members` — a manually-imported OOTP export (not from StatsPlus) giving the *exact* roster of a given draft class. Necessary because StatsPlus's `draft_eligible` flag on `players` is **not** scoped to one class — it's a broad multi-year amateur flag. Always join through `draft_class_pool_members` for "this year's draft pool," never filter on `draft_eligible` alone.

### Transaction/trade analysis — started 2026-08-31 (Rees's ask)
Goal: track trade/transaction history to identify market prices, cross-reference team needs, and eventually suggest transactions — Claude Code builds the analysis, Cowork acts on it (drafting/communicating), same division of labor as everywhere else on this project. Investigated live before building anything (don't re-derive this — see `statsplus-api-inventory.md` if it needs updating):

- **Free agency needs zero new work.** `players.free_agent` is already ingested in bulk. The raw flag alone is noisy (37,050 rows, mostly amateurs who've never been rostered) — filter to `free_agent = true AND last_team_id IS NOT NULL AND last_team_id != 0 AND retired = false` for the real, actionable list (confirmed: 2,262 rows).
- **Trade block — Phase 1, shipped.** `trade_block_snapshots` table + `scripts/scrape-trade-block.ts`, scraping `https://.../thebigleague/tradeblock/` (public, no auth — the player_id→asking-price-note map is baked directly into that page's HTML as a `<script id="tradeblock-pids-data">` JSON blob, one page fetch for the whole league, no per-player scraping). Not yet wired into the automated refresh pipeline — trade block content is GM-driven, not sim-driven, so its own run cadence is still an open decision.
- **Trade history — Phase 2, shipped, then REWRITTEN same day after Rees caught a real accuracy gap.** First version scraped `/player/{id}?page=trade` for the 276 `players.was_traded=true` players and landed at 195 trades. Rees flagged this as suspiciously low against StatsPlus's own `/trade/#recent` tab, which he could see showing **1,101 trades since 2001**. Investigating that tab found the real problem: it's backed by a public, no-auth AJAX endpoint (`/ttajaxtable/?info=recent&view=recent`) that returns the league's entire trade ledger in one ~3-second request — and cross-checking it directly showed only **274 of the 1,749 players actually involved in a real trade have `was_traded=true` (16%)**. The flag itself is badly incomplete; scoping to it was a bad premise, not a scraping bug. **Rebuilt entirely around the ledger endpoint instead** — no player-list dependency at all, one request pulls all of league history. `lib/statsplus-client.ts`'s `playerTradeHistoryHtml()` was removed and replaced with `tradeLedgerHtml()` (probes for the `total` count, then re-requests with `rows=total+50` to get everything in one page — confirmed byte-identical across two independent fetches, so row order is stable). `scripts/scrape-trade-history.ts` is a full rewrite around this endpoint, not a patch.
  - **Verified final state: all 1,101 trades (1,084 complete + 17 pending) and 4,101 items — 2,138 players, 1,700 draft picks, 263 cash entries.** Two entirely new asset types the old per-player-page approach never saw at all: **draft picks** (`trade_event_items.pick_year`/`pick_round`/`pick_team_id`/`pick_team_name` — the pick's *original* team, which can differ from either side of a given trade if it already changed hands once before) and **retained-salary percentages** on player items (`retained_salary_pct`, e.g. a team keeping 50% of a traded player's salary) — directly useful for the still-unsolved "team payroll isn't a simple salary sum" gap below. New `trade_events.status` column (`'complete'`/`'pending'`) carries StatsPlus's own trade-review status through. Confirmed idempotent by test — re-running against already-populated tables reproduces the exact same 1,101/4,101 counts.
  - **Team abbreviations get reused across league history — do not build an abbreviation→team lookup without checking for collisions.** Building an index to resolve a traded pick's original team from its 3-letter code (e.g. "DEN") found two real collisions across 30 years: `BOS` and `NY` each map to two different team ids, almost certainly franchise relocations/renames reusing a short code. The script only resolves a pick's `pick_team_id` when its abbreviation maps to exactly one id across the whole ledger; ambiguous or unseen abbreviations (121 of 1,700 picks, ~7%) keep `pick_team_id` null with `pick_team_name` holding the raw code as a fallback — same "don't guess wrong" principle as the team-resolution gotcha below.
  - **A trade's own team cells resolve far more completely than the per-player page's did.** The old approach hit an unlinked "Durham" team as a hard-to-resolve edge case. The ledger endpoint links that exact same historical trade correctly (to team id 17 — a franchise since renamed to Cincinnati in `teams`, `team_a_name` still preserving "Durham (DUR)" as it read at the time) — **zero trades in the full 1,101 ended up with an unresolvable team side.** `extractTeamRef()`'s null-id/name-fallback path is kept as a defensive backstop, not because it's regularly needed here.
  - **A trade's own free-text "Note:" field (12 found, e.g. "Note: Retain 25%", "Note: Plus Ryan Thompson and the 2008 1st Round Pick from Huron") is GM commentary, not a distinct asset** — every note spot-checked described something *already present* in that trade's own structured player/pick items, never something missing from them. The script logs and skips these rather than treating them as unparseable content.
  - **Trade-key design, carried forward from the first version's own hard-won lesson (see git history if the reasoning is needed) with one adjustment**: since this endpoint returns the complete ledger fresh every time (not fragments merged across many player pages), there's no risk of a parsing fix changing what's captured for an already-keyed trade the way there was before. Key is still `(date, sorted team pair)`, but 31 real combos in this ledger have more than one distinct trade on file (e.g. two separate Carolina/St. Louis deals same day) — disambiguated by position within that group, in the ledger's own fetch order, which is confirmed stable across independent fetches.
  - Not yet wired into the automated refresh pipeline — same open cadence question as the trade block scraper above (run cadence for both still needs a decision: on every StatsPlus refresh, on a slower schedule, or manual-only).
  - `view: "void"` on the same endpoint is a separate 85-row list of *cancelled* trades that never went through — not pulled, not part of the 1,101, flagged here in case it's ever wanted.
- **Two bonus discoveries, not yet used for anything:** `/thebigleague/finance/current/` is a real, game-computed team payroll/budget report — may solve the "team financials" gap below without needing to reconstruct retained-salary math ourselves. `/thebigleague/rosterconstruction/` breaks every team's roster down by acquisition method (draft/trade/FA/waiver/international/etc.) plus a player WAR-vs-salary efficiency table — directly relevant to "team needs" and value analysis.
- Team-needs analysis itself (the next real step) has real raw material already: org-minors depth data, role/level benchmarks, prospect rankings. Likely more an aggregation task over existing data than new ingestion.
- **Trade-value methodology, proposed 2026-08-31 (not yet built).** Goal: score both sides of a trade to answer "who won this" — four components: (1) talent value, reusing existing Overall/Potential/Prospect Potential/role/ETA rather than a new model; (2) contract surplus value — market rate for a player's talent tier (regressed from real league salaries) vs. what they're actually paid, with `retained_salary_pct` (see above) directly discounting the acquiring side's effective cost; (3) a control-years multiplier, discounted for years further out, so a pure rental scores far below a multi-year-control player at the same talent+salary level; (4) draft pick value, built empirically from our own league's real draft-outcome history (round → eventual career value) rather than a borrowed external chart, further discounted for picks further in the future. Combine via a weighted composite (same `rating_weights`/`system_rank_weights`-style tunable-DB-table pattern as everywhere else, not hardcoded), not a full WAR-surplus dollar model — the latter would need an aging/dev curve we don't have enough history to fit reliably yet.
  - **Two real data-availability walls found while scoping this, both now addressed (except history that hasn't happened yet):**
    - Ratings/computed snapshots (`refresh_runs`) only go back to **2031-06-23** (our first successful refresh — coincidentally right around that season's trade deadline). Of the full 1,101-trade ledger, only **2 completed trades** fall on/after that date (both 2031-07-07), plus 17 sitting in the pending-review queue as of this writing. Any trade before 2031-06-23 has no "ratings as of the trade" to score against and never will — those are permanently out of scope, exactly as Rees expected going in. The testable sample grows only as the league keeps simming and trading from here forward.
    - Contract data (`contracts`/`contract_extensions`) was current-state-only — overwritten every refresh, no history — making "contract terms as of a past trade" unreconstructable beyond a short recent window. **Fixed 2026-08-31**: new `contract_snapshots`/`contract_extension_snapshots` tables, same no-FK/sibling/`(refresh_run_id, player_id)`-keyed pattern as every other snapshot table, populated every refresh from the exact same `sp.contracts()`/`sp.contractExtensions()` rows already being pulled for the current-state tables (`refresh.ts`, no second fetch). First real capture: refresh run 25, 13,899 rows each. The existing current-state `contracts`/`contract_extensions` tables are untouched and still serve anything that just wants "the deal right now." **This only accumulates going forward — there is no way to backfill contract history for trades that already happened**, which is exactly why Rees asked to get this capturing now, before the offseason's trading activity.
  - **Contract-classification refinement, 2026-08-31, before building the market-rate curve**: Rees pushed back on a naive salary-vs-Overall regression, correctly — OOTP (like real MLB) pays players on a fixed, escalating scale by service time, totally independent of talent. Confirmed directly in this league's own data: pre-arb averages **$122K**, arbitration-eligible **$2.64M**, free-agent-eligible **$9.30M** — regressing across all of that would mostly measure service time, not skill. Checked every possible better signal before settling on the fix: `players.has_received_arbitration` is the field StatsPlus clearly intends for this and it's simply unpopulated (`false` for all 13,899 non-retired players); no StatsPlus endpoint or report page (finance, roster, free agents) exposes an explicit contract-type flag. Landed on a multi-signal empirical classification instead of a single service-year cutoff: (1) league-minimum salary detected fresh each run as the mode of low-service salaries (confirmed a real, sharp constant — $500,000 as of 2026-08-31 — not a fuzzy proxy); (2) 6+ years of MLB service required (confirmed 85% of 3–5-year arbitration-eligible contracts are exactly 1 year, matching how real arbitration works: awarded one season at a time); (3) excludes anyone also present in `contract_extension_snapshots` (catches a below-market extension signed before free agency — small in practice, 8 players, but a real and free cross-check). Only contracts clearing all three feed the curve; every player (including a rock-bottom-paid rookie) still gets *scored* against it — that gap between the curve's prediction and actual pay is exactly what "surplus value from cost control" means.
  - **Market-rate curve — first piece built and verified, 2026-08-31.** `scripts/compute-market-rates.ts` fits `ln(AAV) = intercept + slope × Overall` via OLS on the clean sample above (log-linear, not linear — pay scales disproportionately with elite talent), then computes a per-role multiplier (each role's real average pay ÷ what the curve alone predicts for their average Overall) — this is where "a top reliever isn't worth what a top starter is worth" gets captured from what this league's own GMs actually pay, not a hand-picked weight. Two new tables, `market_rate_curves` and `market_rate_role_multipliers`, versioned by `refresh_run_id` like `player_computed`/`team_computed` (computed output, not a manually-tuned weight table like `rating_weights`).
  - **First result exposed a real bug, caught by Rees, fixed same day.** The very first version pooled hitters and pitchers into ONE curve — RP's genuinely lower pay dragged that pooled baseline down, making every hitting position look inflated relative to it, and DH came out priced **highest of any role (×2.23)**, above every position that also plays defense. Rees called this out as inherently wrong: DH provides zero defensive value and can never legitimately outrank a position that does. **Fixed with three changes**: (1) split into two separate curves, hitters-only and pitchers-only, fit independently — removes the cross-contamination; (2) every role's raw multiplier is shrunk toward 1.0 by sample size (`shrunk = 1 + (raw−1) × n/(n+25)` — a small sample like DH's n=11 keeps ~30% of its raw signal, a well-supported one like RP's n=75 keeps ~75%) — a standard fix for exactly this "noisy small-sample ratio" problem; (3) DH is explicitly capped at the lowest other hitting-role multiplier post-shrinkage, since no amount of data should ever let DH out-rank a fielder — a domain constraint no regression can infer on its own. **Corrected result** (same 264-player sample): DH now correctly lands at the bottom, tied with C (×0.96, capped down from a raw 1.88) — SP (×1.29) and RP (×0.96) show a sensible, real starter-over-reliever premium now that they're compared only to each other, not blended with hitters. COF remains the one number still worth watching (×1.26, down from ×1.84 pre-shrinkage) — smallest hitting sample after DH (n=23), plausible but not fully trusted yet.
  - `contract_snapshots`/`player_computed` don't always share the same latest `refresh_run_id` — contracts refresh every run (no auth needed), ratings only refresh on a session-authenticated run (rarer, sometimes deliberately skipped). The script finds each table's own latest run independently rather than requiring a match — confirmed real as of this build (`contract_snapshots` on run 25, `player_computed` on run 24) and treated as an accepted, reasonable join (a player's Overall/role rarely shifts meaningfully over a small gap between refreshes) rather than a bug to chase.

### Rating-engine validity check — `/admin/rating-validation`, shipped 2026-08-31 (Rees's ask)
Separate from the trade-value work above — frames a potential future redesign of the grading/weighting system itself by testing whether Overall (and each individual weighted grade that feeds into it) actually predicts real production. Same interactive pattern as `/admin/market-rates` (scatter + regression + hover/click detail panel via explicit `Scatter` handlers, reused deliberately — see `lib/regression.ts`, extracted from `compute-market-rates.ts` so both pages share one OLS implementation).

- **Scope**: real 2031 MLB WAR only (`level_id=1`, `split_id=1` — confirmed the "overall" split; 2/3/21 are situational splits with WAR always 0). Compared against Overall and every raw grade that actually feeds the engine's Overall formula (`lib/rating-engine.ts`): hitters — Contact, Gap, Power, Eye, Avoid-Ks, Speed; pitchers — Stuff, Movement, Control, Stamina, PBABIP. **Potential is deliberately excluded** — it's a forward-looking ceiling projection, not a claim about this year's production, so testing it against this year's WAR wouldn't be a fair comparison the way Overall-vs-WAR is.
- **A real bug caught during verification, not a live-site issue (caught locally before shipping)**: the first version summed `war` across every row returned for a player+2031+level+split — and got an impossible range (individual-season WAR from -55 to +165). Root cause: `player_batting_stats_snapshots`/`player_pitching_stats_snapshots` are **cumulative-as-of-refresh-date time series**, the same pattern as ratings/contracts (documented elsewhere in this doc, apparently not internalized deeply enough the first time this table was queried for a sum) — confirmed directly: one player had 22 rows for the 2031 season, each refresh_run_id's own running total (249 PA at run 3, climbing to a final 692 PA by run 18+), not 22 independent stints. Summing across every refresh_run_id inflated everyone's WAR by roughly how many times they'd been snapshotted. **Fixed**: query only the single latest stats `refresh_run_id`; multiple rows *within* that one run (a real same-season trade producing 2 team-stint rows in one final snapshot) still get summed correctly, just never across different runs. Re-verified after the fix: WAR range came back to a realistic -4 to +12 (hitters) / -3 to +9 (pitchers). **General lesson, worth remembering before writing any new query against a `_snapshots` table**: check whether "sum across all rows for this key" is even the right operation before writing it — for an append-only accumulation table (like `market_rate_training_contracts`) summing everything is correct; for a cumulative-per-refresh snapshot table (ratings, contracts, and now confirmed also true of the stats tables), it is almost never correct, and the failure mode is a plausible-looking number that's actually wildly wrong, not an error.
- **A second real bug, also caught locally before shipping**: `lib/rating-validation-query.ts` exports plain runtime constants (`HITTER_VARIABLES`/`PITCHER_VARIABLES`), which `RatingValidationExplorer.tsx` (a `"use client"` component) imports as real values, not just types. That pulls the WHOLE module into the browser bundle — including a module-top-level `makeSupabaseClient()` call, which then executes in the browser and throws immediately (`SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY must be set`), confirmed via a real dev-server hydration crash. `market-rate-query.ts` has the identical top-level-client pattern but was never triggered, purely because `MarketRateExplorer.tsx` happens to only `import type` from it (type-only imports are erased at compile time, so the module's runtime code, including that top-level call, never actually ships to the browser). **Fixed in both files**: `makeSupabaseClient()` is now called inside each exported function instead of at module top level, so merely importing a module for its types or constants can never execute server-only code. **General lesson**: a data-layer module meant to be safely importable from a client component should never instantiate anything server-only (a Supabase client, an API key read) at module top level — do it inside each function instead, even if nothing currently imports a runtime value from that particular file. The bug is latent until some future edit adds exactly that kind of import, at which point it silently ships a server credential-reading call to the browser.
- **First real results** (516 hitters / 511 pitchers, 2031 MLB): Overall's R² is meaningfully higher than any single raw grade for both player types (hitters: Overall 0.431 vs. best single grade Gap at 0.136; pitchers: Overall 0.453 vs. best single grade Movement at 0.240) — a good sign for the composite formula, as expected (a well-built composite should outperform any one ingredient). **One finding worth flagging as a real, actionable signal, not just a data point**: for pitchers, **Stuff has the *weakest* individual R² of all five grades (0.029)**, while **Movement is by far the strongest (0.240, more than double the next-best, Control at 0.154)** — worth a real look at whether `rating_weights.stuff` is weighted appropriately relative to `rating_weights.movement` once more seasons of data confirm this isn't a one-year fluke.
- **Refined to a rate stat with role-aware minimums, same day, Rees's follow-up.** Raw season WAR was rejected as the target: it rewards playing time as much as talent (an average player at 600 PA out-totals a great one at 200), and it can't compare starters and relievers at all (an ace SP racks up 3-4x an elite RP's innings). Now: hitters are measured on **WAR per 100 PA, minimum 100 PA**; pitchers on **WAR per 100 IP**, but with a **role-dependent innings floor — 75 IP for SP, 30 IP for RP** — rather than one shared number, since a real full-season reliever legitimately throws far fewer innings than a real full-season starter; a single shared threshold would have either excluded most legitimate relievers or admitted token/injured starters. Once both clear their own floor, they're compared on the same per-100-IP rate, which is what actually equalizes them. Both minimums also directly serve the "exclude injured/backup/token-appearance noise" goal — a small, fluky sample isn't a fair test of whether Overall predicted a player's value.
- **Fielding added as a variable, same day, Rees's follow-up.** It's a real weighted contributor to Overall (`overall = max(batting + fielding × w.fielding, pitching)`), just not a single raw grade like Contact — it's itself a derived composite, `max(catcherComposite, infieldComposite, outfieldComposite)`, each built from different raw fields plus a position-specific bonus from the active weight set. Computed in `lib/rating-validation-query.ts` the same way `lib/rating-engine.ts` computes it (not simplified), then tested as one more variable — matching how Overall itself, also a composite, is tested rather than excluded for not being a single raw grade. **First result: Fielding's R² is effectively zero (0.004)** — by far the weakest of any hitter variable. Notable, but flagged here rather than treated as a real finding yet: real-world fielding value is famously the noisiest single-season signal in sabermetrics even with far larger samples, so this could easily be one-year noise rather than a genuine weighting problem — worth specifically re-checking once more seasons accumulate, not acted on now.
- **Updated real results on the refined methodology** (455 hitters / 402 pitchers, 2031 MLB): Overall still meaningfully beats every individual grade for both types (hitters: Overall R²=0.312 vs. best single grade Gap at 0.085; pitchers: Overall 0.319 vs. best single grade Movement at 0.223) — the Movement-over-Stuff gap from the raw-WAR version held up on the harder rate-stat test too (Stuff 0.086 vs. Movement 0.223), reinforcing rather than undercutting that finding.
- Only one season of real outcomes exists so far — treat all of the above as a directional first look, not a final verdict, same framing as the market-rate curve. Gets more reliable every season as more real results accumulate, and the intent (per Rees) is to eventually tie the broader valuation model formally to season stats as that history builds up.

### Rating engine redesign, Phase 1: role-calibrated fielding weight — shipped 2026-08-31
Full proposal (5 weighting options, the anti-overinflation requirement, and the scale-recalibration plan) is a living artifact, not duplicated here — see "Rating Engine Redesign" (published to Rees, ask him for the link if it's needed and not already at hand). This entry covers just Phase 1, now built.

- **What changed**: `rating_weights.fielding` (today a single flat 0.25 applied to every hitter) is now multiplied by a per-role factor from the new `fielding_role_weights` table before being added into Overall/Potential/the H-P split — `lib/rating-engine.ts`'s three `fielding * w.fielding` sites became `fielding * fieldingWeight`, where `fieldingWeight = w.fielding * (fieldingWeights?.[role] ?? 1)`. A role with no entry, or no table at all, behaves exactly as before (multiplier 1).
- **A real reordering was required, not just an addition**: `role` used to be computed *after* `overall`/`potential` in `computeRatings()` — it was purely a display label until now. Moved the `sp_rp`/`role` block earlier (right after `pitchingP`), confirmed safe first by checking that nothing in it depends on `overall`/`batting`/`fielding` — only on raw grades and values already computed above that point.
- **How `fielding_role_weights` gets computed** (`scripts/compute-fielding-weights.ts`, wired into `refresh.ts` after `compute-team-ratings.ts`): reuses `getRatingValidationPoints()` directly (no new data-fetching) to fit a fielding-vs-WAR/100PA slope per hitter role, then runs those seven slopes through an **isotonic regression** (`lib/regression.ts`'s `isotonicRegressionNonIncreasing`, a real pool-adjacent-violators implementation) constrained to the confirmed real defensive-spectrum order (SS > CF > INF > COF > C > DH > 1B), then shrinks each role's result toward the pooled (all-hitters) slope by sample size. This is what makes "a role's fielding weight can never invert relative to another role's" a property of the method, not a hope — shrinking every role toward the *same* central reference point can only pull values closer together, never swap their order, and the isotonic step guarantees the order going in.
- **A real problem found and fixed before this ever ran for real, not after**: the first run produced roughly ×1.7-2.0 multipliers for five of seven roles — a much bigger swing than the data can support, traced to the pooled R² being only 0.004 (fielding is already the weakest predictor of any hitter grade, confirmed above). Shrinkage toward a slope that's itself statistically indistinguishable from noise doesn't fix an overinflation problem, it just relocates it — a large-sample role like INF (n=142) kept 85% of its deviation from a "reference" that wasn't a reliable reference at all. **Fixed with an explicit confidence gate**: if the pooled R² is below 0.02, every role gets a flat multiplier of 1.0 regardless of what any individual role's slope says, full stop. Confirmed this is exactly what fires today — every role currently gets ×1.00, a genuine no-op (verified: the top 5 players by Overall are bit-for-bit identical before and after this change went live). The mechanism is fully built and will start producing real differentiation on its own the moment (if) the underlying relationship strengthens with more seasons — nothing further needs building for that to happen, it just needs to clear the gate.
- **Also capped, defensively, regardless of the gate above**: `relativeMultiplier` is clamped to `[0, 3]` — fielding can never *subtract* value from Overall (a defensive specialist must never rate below an offensively-identical player with worse fielding, which a negative multiplier would do), and can never swing more than 3x today's baseline in either direction no matter what a future season's data says.

### Rating engine redesign, Phase 1 retired and replaced — decomposed offense/defense model (2026-09-01)

**Phase 1 above (role-calibrated fielding weight) is retired, not just dormant.** Measured the actual within-role variance of the two raw grades that both gate role assignment AND feed the Fielding composite: SS's own `ifr` (gate: `≥65`) has SD 3.2 within the SS bucket vs. 11.4 pooled (28% of full spread left); CF's `ofr` (gate: `≥65`) has SD 1.9 within CF vs. 9.9 pooled (19%). This is restriction of range, and it's structural, not a sample-size problem — every SS clears roughly the same `ifr` bar by definition of being called an SS, so there's almost no variance left for a within-role regression to find a relationship in, no matter how many seasons accumulate. The R² confidence gate correctly prevented it from shipping anything untrustworthy, but it was never going to clear that gate for a reason more permanent than "not enough data yet." `compute-fielding-weights.ts`/`fielding_role_weights` are left in place (harmless, still wired into `refresh.ts`, still a confirmed no-op) but should be treated as retired, not "waiting to activate." Full writeup: the "Rating Engine Redesign" artifact (published to Rees).

**Replacement: tune each value stream separately against a real, unconfounded outcome, decide the cross-component blend later** (mirrors how real WAR is built — batting/fielding/baserunning runs measured independently in a shared currency, then simply added, never regressed against each other with role as a variable).

- **Step 1, hit-tool weights vs. OPS+ (`scripts/compute-hitting-weights.ts`)**: pooled across every real MLB hitter (`league_id=200`, `mlb_service_days>0`, ≥100 PA), regresses Contact/Gap/Power/Eye/Avoid-Ks together (multivariate — `lib/regression.ts`'s new `fitMultipleLinear`, normal equations via Gauss-Jordan, no external stats library needed) against OPS+. **R²=0.496** (park-adjusted; 0.502 before park adjustment) — far stronger than any single-grade check this session found, because OPS+ isn't restriction-of-range confounded (role gates on `ifr`/`ofr`, never on hit-tool grades) and because this is the first time these grades were tested together instead of one at a time. Findings: **Contact and Power come out essentially tied** (standardized 0.521/0.521; today's weights treat them as meaningfully different, 0.375/0.325). **Eye looks overweighted today** (implied ~0.09 vs. today's 0.15). **Gap** close, maybe slightly underweighted. **Avoid Ks nets to ~0** once Contact is in the model — not a real "strikeouts don't matter" finding, Contact already bakes in Avoid-Ks+BABIP (confirmed with Rees, see `[[ootp-grade-composites]]`-style note — Contact IS a composite of exactly these). **Diagnostic only, nothing written to `rating_weights` yet** — a real decision for Rees before any of these numbers ship.
- **OPS+ didn't exist anywhere in this schema before this** (`player_batting_stats_snapshots` only has raw counting stats) — built the minimum real version needed: league-wide OBP/SLG from every real 2031 MLB PA (not just the ≥100 PA regression subset — restricting the league baseline to qualifiers would bias it upward), each player's OPS+ relative to that baseline. This is the same league-average-by-level-and-year normalization the "Not built yet" OPS+/FIP- item below already flagged — scoped here to exactly what this one regression needs (2031, MLB level only), not the general system.
- **Ballpark factors, added same day (Rees's ask, after seeing OPS+ ignored park effects entirely)**: new `ballpark_factor_snapshots` table (`refresh_run_id`, `team_id`, `average`/`doubles`/`triples`/`home_runs` + RHB/LHB splits on average and HR, capacity, stadium type, surface), captured every refresh via `scripts/scrape-ballpark-factors.ts` (wired into `refresh.ts` after `compute-team-ratings.ts`, own try/catch). Source: `https://atl-02.statsplus.net/thebigleague/ballparks/` — **confirmed public, no auth/token needed** (unlike ratings/gamehistory). **Team mapping verified directly, not assumed**: every park's `/park/{id}` URL id is identical to our own `team_id` across all 32 real teams (cross-checked against `teams.name || ' ' || teams.nickname` matching the page's `data-name` exactly) — the scraper still logs a warning if a name ever drifts, as a staleness check, but doesn't need name-matching to do the mapping. **Two real limits, both by design, not oversights**: (1) StatsPlus only publishes CURRENT factors — checked both the ballparks index and an individual park page directly, no year selector, no per-season history anywhere on the site — so this is snapshot-forward-only, accurate from 2026-09-01 on, NOT retroactively reconstructable for a relocated/renovated park from before this table existed. (2) Park attribution is per-stint (`player_batting_stats_snapshots.team_id`/`stint`, already granular enough for a traded player's stats to split correctly by team), but NOT per-plate-appearance/home-vs-road — that needs game-log data (deliberately deferred, see below) — so the standard sabermetric approximation is used instead: only **half** of a team's factor deviation from 1.0 is applied (`1 + (factor-1)*0.5`), since a player accumulates roughly half their PA at home and half spread across every other park.
- **OPS+ now applies separate Doubles/Triples/HR adjustments** (Rees's explicit ask, not one blended power factor): each stint's hits are decomposed into singles/doubles/triples/HR, each category divided by its own half-applied park factor (singles use the page's "Average" factor as the closest available proxy — OOTP doesn't publish a standalone singles factor), THEN recombined into OBP/SLG. Walks/HBP are left unadjusted (same as real-world practice — not meaningfully park-driven). League baseline stays raw/unadjusted on purpose (a real MLB league average is never itself park-adjusted either) — only individual players get adjusted, so their park-neutral rate compares fairly against that shared baseline. **Measured impact**: moves individual players' OPS+ by an average of 2.7 points, up to 11.6 for the most extreme park — real and worth having at the player level, even though it barely moved the aggregate regression weights (the park effects aren't correlated with hit-tool grades, so they wash out in the pooled fit).
- **Baserunning composite, new (Rees's ask, `scripts/compute-baserunning-weights.ts`)**: found `run` (general baserunning instincts), `steal` (stealing skill), `stlrt` (stealing tendency/aggressiveness) sitting in `player_ratings_snapshots` fully populated (113,593/113,593 non-pitcher rows, real 20-80 grades) and read by **nothing** in `lib/rating-engine.ts` before this. Regressed all four baserunning-relevant grades (these three plus `speed`) against real **UBR per 100 PA** (StatsPlus already computes UBR as a real per-season baserunning-runs stat, confirmed 647/647 populated, averaging ~0 like a runs-above-average stat should — converted to a rate the same way raw WAR was, since it's a counting stat). **R²=0.553** — even stronger than the hitting regression, a real validation that baserunning value is substantial and simply invisible to OPS+ (a stolen base isn't a hit). `run` dominates (standardized 0.556, ~72% of the implied weight) — almost certainly because it's StatsPlus's own summary baserunning grade, already blending speed/instinct/decision-making, leaving little independent signal for `speed`/`steal` alone (~5% each) once it's in the model. `stlrt` carries real independent signal beyond `run` (~19%) — how often a player's ability actually gets used, distinct from how good that ability is. **Built into `lib/rating-engine.ts`**: new `baserunning` composite (`speed*w.baserunning_speed_weight + run*w.baserunning_run_weight + steal*w.baserunning_steal_weight + stlrt*w.baserunning_stlrt_weight`, weight defaults = this regression's output), computed and stored on `player_computed.baserunning` every run, but **`w.baserunning` (its blend weight into Overall/Potential) defaults to 0 — a deliberate no-op**, per Rees: tune Batting/Fielding/Baserunning independently first, decide the three-way blend weight later. Confirmed true no-op end to end (top-5 Overall bit-for-bit identical before/after). **`speed` deliberately stays in Batting too** — not moved out — per Rees: faster batters beat out more grounders/take extra bases, a real batting-outcome effect distinct from the Baserunning composite's own value; the small overlap is accepted, not a bug.
- **Per the OOTP wiki (Rees quoted it directly)**: Speed is offense-only, does NOT affect steal ability or attempt frequency (that's what `steal`/`stlrt` are for) but does affect advancing on balls in play/scoring/stretching hits into extra bases — consistent with keeping it in Batting separately from Baserunning.

### `/admin/weight-tuning` — visualizing and tracking the three regressions above (2026-09-02)

### Checked, not built: a Power version of the Contact/Control weak-tool gate (2026-09-02)

- **Residual check on real performers**: fit the same linear hitting model, then looked at whether low-Power real MLB regulars (100+ PA) do systematically *worse* than even the linear model already predicts (which would mean a linear weight can't capture the effect — the same argument that justified gating Contact/Control). - **Direct scan of real low-Power cases** (`pow <= 25`, no PA filter): no anomalous overvaluation found — every real player with a genuinely weak Power grade has an Overall that lands roughly where their other (also modest-to-average) grades would suggest, nothing resembling the "elite everything else, unplayable primary tool, absurdly high rank" pattern that justified Contact/Control.

### Real bug found and fixed: standardized coefficients were being used as literal weights (2026-09-02)

Caught via a real anomaly Rees spotted: **Jeremy Porten** — the single highest Batting composite (70.0) of any hitter in the league, average Fielding (50), well-below-average Baserunning (25.4), a real 7.1 WAR season — was ranked outside the top 100 (rank 103). Also flagged: pitchers heavily overrepresented in the top 100 (72 of 100).

**Root cause, confirmed with real numbers, not assumed**: every regression this session normalized *standardized* coefficients (clamp negatives to 0, rescale to sum to 1) and used that as the literal multiplier applied to *raw* composite/grade values. Standardized coefficients answer "how much does a 1-SD move in X affect Y" — the right lens for judging relative importance (still shown on the page for that reason), but applying them directly to raw values silently reintroduces each variable's own scale, which is exactly what standardizing was supposed to control for. Checked the actual population variances among real MLB hitters:

| Composite | Weight (before fix) | Population SD | Weight × SD (real ranking influence) |
|---|---|---|---|
| Batting | 0.567 | 4.9 (compressed — average of 6 grades) | 2.78 |
| Fielding | 0.271 | 8.2 | 2.22 |
| Baserunning | 0.161 | 17.5 (barely compressed — one grade, `run`, is 71.5% of its own formula) | **2.82** |

Despite Batting's weight being 3.5x Baserunning's, Baserunning's 3.5x larger variance gave it *slightly more* real influence on rankings — silently erasing the intended "batting is king" hierarchy. The fix: normalize **raw** (unstandardized) coefficients instead — already expressed in real per-unit terms, the dimensionally correct thing to apply to raw values. Fixed in all four `compute-*-weights.ts` scripts.

**New active `rating_weights` row (id=6)**, all four domains recomputed under the corrected methodology:
- **Batting/Fielding/Baserunning blend**: 0.567/0.271/0.161 → **0.708/0.245/0.047**. This is the one that mattered — Porten's rank went **103 → 15**, Overall 57.4 → 63.7.
- **Hitting**: Contact 0.465, Power 0.377, Eye 0.090, Gap 0.046, Speed 0.022, Avoid Ks 0 (was 0.403/0.414/0.098/0.045/0.040/0 — modest shifts, these six inputs already had comparable variances to begin with).
- **Pitching (WAR target, chosen approach)**: SP → stuff 0.257/movement 0.512/control 0.174/stamina 0.057 (was 0.297/0.420/0.193/0.090). RP → stuff 0.294/movement 0.462/control 0.189/stamina 0.055 (was 0.412/0.322/0.185/0.081). Movement's real importance was understated more than expected by the old method.
- **Baserunning internal weights**: run 0.648, stlrt 0.244, steal 0.055, speed 0.054 (was 0.715/0.190/0.048/0.046 — modest shift, same reasoning as hitting).

**A second, related staleness bug fixed in `compute-overall-blend-weights.ts` while working on this**: its "current weight" comparison hardcoded `Batting: 1` from before the real `batting` column existed, so it never picked up the real value even after batting's weight shipped. Now reads the real column.

### Hitter/pitcher rescale: the real problem, then the fix (2026-09-03)

### Calibration floor: 20 → 0 → replaced entirely with a level-anchored ladder (2026-09-03/04)

The rescale above needed *some* floor at first (a raw value far enough below the reference-population mean produces a negative z-score) — but the floor itself went through real iteration once its side effects became visible on real players, not just an abstract population stat.

- **Floor=20 → 0 (2026-09-03)**: floor=20 (mean − 3 SD of the *narrow* MLB-reference SD) flattened a large swath of low-level players to an identical "20" — the narrow SD that correctly differentiates elite MLB talent badly over-stretches anyone far below it. Lowering to 0 (mean − 5 SD) freed ~3,900 players but **still flattened 34% of the full population (4,791/13,907)** to an identical 0, including 426 real full-season A/A+ prospects — confirmed the floor *value* was never the real problem, just where the pileup happened to land.
- **Real example that forced the actual fix (2026-09-04)**: Lance Angstman (OKC, A+), current Contact 30 / Power 45 / Fielding 35 / Baserunning ~26 — raw Overall 33.3, calibrated to a flat **0**. Rees's initial read ("his current value should be higher, he's a productive A+ bat") turned out to be based on comparing against `batting_p` (Batting *Potential*, 42.7) rather than current Batting (33.2) — but the deeper, real question (why does a reasonably-toolsed player read as an absolute floor value) led to the actual root cause: raw 33.3 is **5.3 standard deviations** below the reference mean on a ruler built exclusively from real, established MLB regulars (a necessarily narrow population — everyone in it already cleared the bar of being rosterable). Removing the floor entirely would have made it *worse* (calibrates to ≈ −3.4, not higher) — confirmed by direct calculation before concluding the floor itself wasn't the lever to pull.
- **The actual fix: a two-piece calibration.** At/above the real MLB mean, calibration is **unchanged** — same validated z-score formula. Below it, calibration is a **piecewise-linear interpolation through this run's own real level averages** instead of a statistical z-score:
  ```
  CalibratedX = interpolate through (typeMean,50), (avgRaw[AAA],45), (avgRaw[AA],40),
    (avgRaw[A+],35), (avgRaw[A],30), (avgRaw[A-],25), (avgRaw[Rookie],20), (avgRaw[International],15)
  ```
  Answers a fundamentally different question below the mean than above it: not "how many SDs from the MLB average," but "which real level's typical player does this look like." Below the lowest anchor (International), the last segment's slope **runs free rather than flattening at a floor** (Rees's explicit call, symmetric with the no-ceiling call above) — confirmed **zero players hit any floor** across the full 13,907-row population post-change (minimum value −1.9, a real number, not a repeat).
  - **New table `calibration_level_anchors`** (`refresh_run_id`, `player_type`, `level` 2-8, `avg_raw_overall`, `n`) — one row per type per level per run, recomputed automatically every refresh from that run's own data (same "never hand-tuned" principle as `typeMean`/`typeSD`), giving a visible history of how each level's real average drifts. `level` here is the corrected canonical scale (see the level-mislabeling fix immediately below) — built *after* that fix, so A+ and A get genuinely separate anchors, not a merged one.
  - **Angstman's real before/after**: Overall 0 → **24.3**, Potential 17.2 → **34.0**, Prospect Potential 4.4 → **28.2**.
  - Implementation: `compute-ratings.ts`'s `calibrate()` — the above-mean branch is byte-identical to before; the below-mean branch replaced the old flat-SD/floor math entirely.

### Explored and rejected: anchoring the level ladder on Batting alone (2026-09-04)

Real per-role breakdown of the level-anchored calibration above surfaced a genuine, known characteristic (not a bug): pooling every role together to build the level anchors means roles with baked-in positional bonuses (C/SS/CF/COF — fielding bonuses, historically-neutral batting multipliers) calibrate a half-level to a full level *above* their target, while roles with little/no defensive value (1B/DH) or the reliever discount (RP) calibrate *below* it. SP tracks closest to target since it's closest to the population average.

- **Explored**: building the level anchors from raw `batting` alone (Batting's own position multipliers are currently neutralized at 1.0, so it's already far more role-neutral than blended Overall). Computed real numbers: this genuinely fixes 1B/DH (their old under-calibration was entirely Fielding's near-zero contribution dragging them down) — but **flips catchers from over- to under-calibrated**, since removing Fielding from the picture entirely also removes the real compensation the catcher bonus exists to provide for catchers' genuinely-weaker-than-average bats.
- **Conclusion, not implemented**: this isn't a fix, it relocates the distortion — Overall genuinely blends two components (Batting, Fielding) that each carry their own role-based skew in opposite directions; anchoring on either alone will always misrepresent whichever role leans most on the other one. The complete fix would be calibrating Batting and Fielding *separately*, each through its own role-neutral ladder, then blending the calibrated results — a real architecture change, not an anchor tweak. **Rees's call: leave as shipped** — the current role-based deviation from target (positional scarcity showing through) is accepted as fit for purpose, not pursued further.

### Trade-value composite: Phase A step 1, control-years multiplier (2026-09-04)

## 6. Gotchas already discovered (save yourself the rediscovery time)

1. **No foreign keys between `player_computed`/`player_ratings_snapshots`/stats snapshot tables.** They're sibling tables independently keyed by `player_id` + `refresh_run_id`, not parent/child. Supabase's automatic embedding (`select("*, other_table(...)")`) **will fail** with "no relationship found" between any two of these. Fetch separately and join in JS (see `fetchComputedPlayers` in `lib/queries.ts` for the pattern) or write raw SQL.
2. **Supabase caps a single `.select()` at 1000 rows by default.** Always paginate with `.range(from, to)` in a loop when you might have more than 1000 matching rows (players table alone is ~45,000 rows). See `fetchAll()` in `lib/queries.ts`.
3. **Import extensions matter and differ by context.** Files under `scripts/` run via `tsx`/Node's ESM loader and **require** explicit `.js` extensions on relative imports (`from "./foo.js"` even though the file is `foo.ts`). Files under `app/` and anything only consumed by Next.js's webpack bundler (like `lib/queries.ts`) **must not** have the extension (`from "./foo"`) or the build fails with "Module not found." This split is intentional, not a mistake to "fix" — don't add `.js` back to `lib/queries.ts`'s imports.
4. **Next.js dev server caches Supabase responses across external database changes.** If the backend session runs a refresh/recompute script while your dev server is running, the page will keep showing old data. `rm -rf .next` and restart `npm run dev` to see fresh data. There's no code fix for this yet — just a routine to remember.
5. **League level codes need decoding, and it's not obvious from the number alone — and `level` alone is not enough, `league_id` matters too.** `0`=unassigned, `1`=MLB, `2`=AAA, `3`=AA, `5`=A-, `6`=Rookie — **but `4` is NOT a single level.** Corrected 2026-09-04, a real bug found by Rees naming actual OKC affiliates (Wellington=A+, Napanee=A, Trenton=A-): `players.level=4` secretly contains TWO distinct real leagues, distinguishable only by `league_id` (203=A+, 204=A) — confirmed universal across all 32 orgs (each has exactly one team in each league_id), not an OKC quirk. Every other level was already clean. Use `effectiveLevel(level, league_id)` from `lib/display-helpers.ts` (the one shared, canonical implementation — previously duplicated across 3 files, none of which knew about this split) plus `levelLabel()` on its result, never the raw integer or `level` alone. Canonical scale is now 8 tiers, not 7: 1=MLB, 2=AAA, 3=AA, 4=A+, 5=A, 6=A-, 7=Rookie, 8=International (see gotcha 19, now superseded/consolidated by this fix). Full writeup, every consumer touched, and verification: see "Real data-model bug: `players.level=4` covers two real leagues" in §4 above.
6. **A "prospect" is not simply "anyone with `prospect_rank` set who has no org."** Free agents only belong in prospect rankings if they have a real `last_team_id` (previously rostered — a "true" free agent). Free agents with no `last_team_id` are almost always amateur draft-pool players who've never been rostered, and the *vast majority* of those are years away from being relevant (future draft classes). This filter already lives in `compute-ratings.ts` (backend), so `player_computed.prospect_rank` is already correct — just don't re-derive "is this a prospect" from raw `players` fields yourself; trust `prospect_rank is not null`.
7. **Stats endpoints are split by league/level — a season can have multiple rows per player.** See §4. `getTopProspectsDetailed`'s `seasonStints` array is the pattern to follow if you need per-level season stats anywhere else.
8. **StatsPlus's `lid` parameter is a trap, in two opposite directions.** On `playerbatstatsv2`/`playerpitchstatsv2`/`playerfieldstatsv2`, *omitting* `lid` silently scopes results to MLB only (`lid=200`) — there's no "all levels" shortcut, so the refresh script loops over every level's `lid` (200/201/202/203/204/205/206 = MLB/AAA/AA/**A+/A**/A-/Rookie — 203 and 204 are two genuinely different real levels, not "two parallel A+ leagues" as originally assumed here; see gotcha 5) per year. This bit us once already — a version of the refresh script that never passed `lid` looked completely successful (200 OK, real rows, no errors) while quietly capturing zero minor-league stats. On `teambatstats`/`teampitchstats`, it's the opposite: `lid` is silently *ignored*, and those endpoints only ever return MLB teams no matter what you pass — looping `lid` there just re-fetches identical rows (and will violate a DB uniqueness constraint on the second pass). See `platform/statsplus-api-inventory.md` for the full writeup.

11. **International-complex / not-yet-formally-rostered amateur signees have no team of their own — they hide inside the MLB roster, and `level` alone can't tell them apart.** Discovered 2026-08-19 building `/org-minors`. StatsPlus has no separate team entity for an org's international academy: those players are ordinary `players` rows with `team_id` = the org's own MLB team and `level = 1`, identical to real MLB players on paper. The only tell is **`league_id`**: real MLB roster players carry `league_id = 200` (same value as the `LEAGUE_IDS` used for stats pulls); international/complex signees carry a **negative** `league_id` — confirmed `-200` for org 15 (Oklahoma City): 34 players at `league_id = 200` (ages 22–33, a normal active roster) vs. 60 at `league_id = -200` (ages 16–19, confirmed against a real player Rees named). If you're building anything that means "the real MLB roster" or "the international group," filter on `league_id`'s sign, not on `level`/`team_id` alone, or you'll either drop these players silently or lump them in with the actual MLB roster. Working implementation: `lib/org-minors-query.ts`.
    - **Confirmed league-wide 2026-08-31, and found a real (small) crack in it while building the Overall-rescale proposal.** Checked every org's `league_id ∈ {200, -200}` age distribution directly: the split holds cleanly almost everywhere — every org shows a clean ~17-18-year-old cluster at `-200` and a ~27-29-year-old cluster at `200`. But it's not perfectly clean: **7 individual player records (concentrated in a few orgs, e.g. org 6) are mislabeled straight into `league_id = 200` despite being 17-20-year-old international-type profiles** — confirmed by their `league_id = 200` min age (17-19) sitting far below every other org's `200`-bucket minimum (21-27). This isn't a systemic convention failure, just a handful of individual data-quality stragglers — but it's exactly the kind of thing that silently poisons any calculation treating `league_id = 200` alone as "real MLB players": it was found because it dragged a real-MLB-average-Overall calculation's minimum down to 26.9 (nearly 6 SD below the mean).
    - **Fix refined the same day, Rees's correction: age is a proxy, not the real identifier — `mlb_service_days` is.** An `age ≥ 20` guard worked (dropped exactly the 7 stragglers, all confirmed `mlb_service_days = 0`), but Rees correctly rejected age (and, separately, draft status — plenty of real MLB talent signs internationally rather than through the draft, so "went through the draft" isn't a valid proxy for "is real MLB talent" either) as the wrong signal to hang this on: nothing about being young or undrafted actually means "hasn't cracked an MLB roster," it just happens to correlate with it in this specific straggler case. **`mlb_service_days > 0`** is the direct, correct identifier — literally "has this player ever accrued real MLB roster time," independent of age, draft status, or signing route. Verified it's strictly better: filtering on it instead of age caught *more* contamination (13 records, not 7) and produced a cleaner reference population (min jumped to a believable 49.9, SD tightened further to 5.2). Checked the obvious failure mode before trusting it — a genuine rookie debuting this season with real playing time but zero prior service days — and found none: every player with 50+ real 2031 PA already shows accrued service days by this point in the season. **The corrected filter is `league_id = 200 AND mlb_service_days > 0`.**
    - **Scoped deliberately: this belongs in reference-population/statistical calculations, not on `/org-minors`.** Confirmed with Rees directly — that page's whole job is showing the complete org, international signees included, so filtering any of them out there would be wrong, not a fix. The `mlb_service_days > 0` guard is for anywhere computing a statistic meant to represent "real MLB talent" (the Overall-rescale work); it is **not** a blanket rule for every `league_id = 200` usage in the codebase.

13. **Any Supabase `.range()` pagination without an explicit `.order()` has no stability guarantee — this was silently producing a different "top 100" on every page load.** Discovered 2026-08-19 chasing what looked like a broken delta calculation: `fetchComputedPlayers`'s base `players` query (`lib/queries.ts`) had no `.order()`, so Postgres/PostgREST was free to return rows in a different order across separate requests. Any new pure display helper a client component might need goes in `display-helpers.ts`, not `queries.ts` — check this before adding one. Also cost real debugging time because the failure looked like a stale-cache issue at first (this session's console-log tooling appears to persist old errors across navigations within the same tab — a brand-new tab showed the real, current state cleanly and settled it).

18. **`players.is_active` is a level-1-only concept — every level 2-6 row has it `false` unconditionally.** Confirmed by direct query 2026-08-24 while building the role-aware ETA model: "active roster" isn't something OOTP tracks for minor-league rosters, only the majors. 19. **International/complex signees need their own explicit remap wherever `players.level` drives real logic — they don't have a level code of their own.** Direct fallout of the gotcha above and the org-minors one before it: after gating the MLB benchmark row to `is_active = true`, international signees (level=1, negative league_id) weren't polluting that row anymore, but they'd also become entirely invisible to the Role × Level benchmark table AND — a real correctness bug, not just a display gap — an individual international prospect's OWN `estimateEta()` call was reading their raw `level` as 1 and short-circuiting straight to "already at the majors" (this specific shortcut no longer exists at all as of gotcha 20 below, but the fix here — the `effectiveLevel` remap — is still current and still needed for the benchmark table and the sanity-gate check). 20. **ETA reworked a second time the same day (2026-08-24) — Rees generalized his own fix.** The version in gotcha 19 (role-aware, real levels-to-climb, potential-driven pace) still had a real blind spot: it counted distance using the player's literal ROSTER level, so a player already performing at an MLB-caliber level for his role but stuck at (say) A+ behind a logjam still got a multi-year ETA purely because of where he was rostered. 32. **Potential now has real (extrapolated) L/R split data of its own, 2026-08-28 — Rees's spec, closing a real anomaly he spotted directly.** He noticed Jeremy Porten showing Overall (83.3) *higher* than Potential (82.6) and asked why. Root cause traced exactly: Current Batting/Pitching have blended by real league handedness exposure since 2026-08-24 (gotcha 21), but Potential never got the same treatment — there's no `pot_*_l`/`pot_*_r` data from StatsPlus, so Potential kept reading the flat `pot_*` field directly. For any player whose current L/R split is asymmetric in the right direction, that alone can push blended Current above flat Potential, with nothing wrong in either number individually.
    - **Empirical finding, worth remembering**: the flat CURRENT grade is not a fixed function of its own L/R split. Real examples, same field: one player's flat Power exactly matches his R-side grade, another's matches his L-side grade, a third's sits at neither — confirmed across a real sample before designing anything, ruling out any single hardcoded convention like "flat = vs-RHP."
    - **Method** (`projectPotentialSplit()` in `lib/rating-engine.ts`): for each split-eligible grade, compute `t = (currentFlat − currentR) / (currentL − currentR)` — exactly, from real observed current data, not assumed — and the real differential `d = currentL − currentR`. Project `pot_R = pot_flat − t·d`, `pot_L = pot_flat + (1−t)·d`. Both of Rees's stated requirements hold **exactly by construction**, not approximately: `pot_L − pot_R` always equals the real current differential, and interpolating `pot_L`/`pot_R` by the same `t` always reproduces the known flat `pot_flat` value exactly. `t` is clamped to `[0,1]` as a guard against rounding noise pushing current flat slightly outside `[L,R]`; a null/near-zero-differential input falls back to `{l: flat, r: flat}`. **Explicitly flagged to Rees as a genuine estimate, not a recovery of ground truth** — every input here is itself a rounded proxy for a hidden continuous value (his own framing), so this carries the current relationship forward, it doesn't observe the true future one.

## 7a. Automated data refresh (2026-08-28)

The refresh pipeline is now fully automatic — nobody needs to open Claude Code, copy a StatsPlus cookie, or run `npm run refresh` by hand anymore, for a normal sim. Full design history and the options considered/rejected are in the conversation this shipped from; this section is the durable reference.

- **`.github/workflows/refresh.yml`** runs on its own GitHub Actions schedule (`*/30 * * * *`, every 30 min — GitHub doesn't guarantee exact timing, fine for this) plus `workflow_dispatch` for a manual/forced run. Fixed by bumping to Node 22. (2) `scripts/compute-team-ratings.ts` still used a plain `.insert()` for `team_computed`, the same class of bug already fixed for `player_computed` in gotcha 31 — just never ported to this script. A transient network hiccup lost the success response for an already-successful write, the retry collided with its own prior insert on `(refresh_run_id, team_id)`, and the whole run reported failure even though the underlying data was already fully correct (confirmed 32/32 rows via direct query before touching anything). **Architecture — deliberately NOT full Supabase Auth.** With exactly one privileged user (Rees) and an undifferentiated, no-login guest tier, real accounts/sessions would be meaningfully more to build and maintain for a capability nobody asked for (telling individual guests apart). Instead: a single shared owner password, an HMAC-signed cookie, and Next.js Middleware gating every route. This is a **page-visibility gate only, not a data-security boundary** — the real protection is the Supabase RLS default-deny setup from §3, completely independent of this system and unaffected by it.

- `lib/owner-cookie.ts` — `expectedOwnerCookieValue(secret)` HMAC-SHA256-signs a fixed payload using Web Crypto (`crypto.subtle`, not Node's `crypto` module — needed because Middleware runs on the Edge runtime, which doesn't have Node's `crypto` or a reliable `Buffer`). The signature itself (not the password) is what's stored in the cookie.
- `middleware.ts` — runs on every request except static assets. If a valid signed `dsa_owner` cookie is present, the request passes through untouched (owner: every route). Otherwise, only `GUEST_ALLOWED_PATHS` (`/TBL/prospects`, `/login`) are allowed through; everything else redirects to `/TBL/prospects`. **To open up a new page to guests, add its path to `GUEST_ALLOWED_PATHS` — no other code changes needed** (or nest it under an already-allowed path, like `/TBL/prospects/farms` did — the prefix match already covers it).
- `/login` (`app/login/page.tsx`) + `/api/login` (`app/api/login/route.ts`) — a plain password form. Correct password → sets the signed cookie with a 1-year expiry (Rees's "automatically logged in thereafter" spec) and redirects home; wrong password → back to `/login?error=1`.
- **"Preview as Guest" toggle, added 2026-08-25.** Lets an already-logged-in owner see exactly what a guest sees without logging out. Second cookie, `dsa_preview_guest` (name in `lib/owner-cookie.ts`), deliberately *unsigned* — it can only ever narrow an already-verified owner's access, never grant access to anyone who doesn't already have a valid `dsa_owner` cookie, so it doesn't need HMAC protection. `middleware.ts` only takes the full-access branch when the owner cookie is valid **and** this one is absent; toggled via plain `<a href>` GET requests (not `next/link`'s `<Link>`, which prefetches links in view by default — a prefetched state-changing GET would silently flip the toggle before anyone clicked it) to `/api/preview-guest?action=enter` / `?action=exit`, which redirect back to wherever the click came from (`Referer` header, with a sane fallback). That route is a no-op for anyone without a real owner cookie — verified live: clearing the owner cookie and hitting the URL directly does nothing. Display logic needs `isRealOwner` and `isPreviewingGuest` as two separate booleans, not one combined `isOwner` — a genuine guest and an owner-previewing-as-guest see the same restricted pages, but the header still needs to tell them apart (guest gets "Owner Login"; previewing owner gets "Exit Guest Preview" instead, since they don't need to log in again). `SiteNav.tsx` (owner pages) shows "Preview as Guest"; `ReportHeader.tsx` (`/TBL/prospects` pages) shows the three-way state on the right side of the nav.
- Cookie comparison is a plain `===` string check, not constant-time — an accepted low-stakes tradeoff (this gates page-visibility *timing*, not real data).
- Required env vars (Vercel dashboard only — no MCP tool exists to set these, and Claude Code must never enter secrets into a field itself): `OWNER_PASSWORD` (what Rees types at `/login`) and `OWNER_COOKIE_SECRET` (internal HMAC key, opaque random string). Both generated once and handed to Rees to paste in himself. `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are also required at **build time**, not just runtime — confirmed 2026-08-24: `lib/queries.ts` and `lib/org-minors-query.ts` both create their Supabase client at module scope, which Next.js's "Collecting page data" build step touches even for `force-dynamic` pages (it still has to statically analyze the root layout). No env vars → the build itself fails, not just the deployed app.

**Three real N-scan performance bugs found and fixed in `lib/queries.ts`, 2026-08-25.** Rees flagged `/TBL/prospects` as slow to load (both for him live and visibly in this session's own dev-server request logs: 20-23 seconds per load). All three bugs shared the same shape: fetch an entire large table unfiltered, in JS-paginated 1000-row chunks, just to derive a small result — instead of pushing the real filter/sort/limit down to the database query itself.

1. **`fetchComputedPlayers()`** (powers `/players`, `/draft`, and — via `getTopProspectsDetailed` — `/prospects`/`/TBL/prospects`) used to fetch the `players` table FIRST — unfiltered, up to the full ~45,757-row table when no `orgId`/`playerIds` scope applied, which is exactly the leaguewide default view both prospects pages use — then chunk-fetched `player_computed` and `player_ratings_snapshots` for **all** of them in batches of 500, and only THEN sorted and sliced down to the actual 500 needed, in JS. That's 230+ sequential round trips to build a 500-row list. Fixed by querying `player_computed` FIRST, with the sort (`overall`/`prospect_potential` descending) and limit (`+50` buffer for safety) applied IN the query — then only fetching `players`/ratings for that much smaller resulting set. The org-scoped case (one team) was already fine and is unchanged in shape, just now also limited at the DB level for consistency.
2. **`getOrgTeams()`** (powers the team filter dropdown on every list page, and `getTeamRankings()` for System Rankings) used to fetch every player's `organization_id` — again up to the full ~45,757-row table, unfiltered — just to build a Set of which of the ~30-40 candidate "parent" teams actually have players attached (filtering out placeholder/conference rows like "ODC Fire Conference"). Fixed by getting the small candidate team list first, then checking each candidate for at least one matching player **in parallel** (`Promise.all`, not sequential) — wall-clock cost is now roughly one round trip, not ~46 sequential ones.
3. **`getProspectSnapshotOptions()`** (powers the "Change from" baseline picker) — this was the dominant remaining cost once the two above were fixed, confirmed by temporarily instrumenting every step with `console.log` timers (removed before committing) and finding the actual query work totaled ~1.4s while the reported request time was still ~6.9s. It used to fetch `refresh_run_id` from **every row** of `player_computed` — one row per player *per historical refresh run*, so potentially hundreds of thousands of rows — just to dedupe down to a handful of distinct ids, exactly the comment already flagged as a future risk ("worth revisiting if this ever gets slow"). Fixed the same way as `getOrgTeams`: query the small `refresh_runs` table first (one row per actual refresh event, capped at the 30 most recent — plenty for a "change from" picker), then confirm each candidate has a real `player_computed` snapshot via small parallel existence checks.

**Net result, measured directly in dev server logs (warm request, no compile overhead): ~20-23 seconds → ~1.6-1.9 seconds.** Verified correctness held throughout, not just speed: `/TBL/prospects`'s rankings (#1 R.J. Blum, #2 J.P. Schall, ...), row count (1000 = 500 players × 2 rows), the "Change from" dropdown's two dates, `/TBL/prospects/farms`'s team order (#1 Fort Collins Roosters, ...), and the org filter's full 32-team list all matched exactly what they showed before any of these changes. **If a future page feels slow, check for this same pattern first** — an unfiltered `fetchAll()` over `players` or `player_computed` with no `.limit()` pushed into the query is the one to look for; both are large, frequently-queried tables where "fetch everything, filter in JS" silently turns into hundreds of sequential round trips as the league's history grows.
